1. Introduction

This threat model covers WebMCP specifications and integrates some implementation elements to provide a clearer view. WebMCP is a browser-side API surface that allows a web document to expose page functionality as structured tools that can be discovered and invoked by browser-integrated or in-page agents (e.g., PageAgent). WebMCP does not create every threat considered in this model. These can be derived from Agentic navigation, MCP-style tool mediation, and WebMCP-specific features.

Note: WebMCP is not a backend MCP deployment. Instead, it brings MCP-like tool interaction into the browser by reusing an existing web application’s functionality and state and exposing that functionality to agents through browser-side mechanisms.

1.1. Terminology

This threat model uses the terminology defined in the WebMCP specification and its accompanying explainer.

1.3. Methodology

This threat model follows the W3C Threat Modeling Guide. It begins by modeling the system under analysis and identifying its elements, data flows, and trust boundaries.

Threat elicitation uses STRIDE as a first pass across those elements and flows. PHANTOM-B complements this analysis for threats associated with the LLM-dependent parts of the system.

The model also draws on the Threat Model for the Web and its Web Security Model, particularly the concepts of origin, isolation, browser mediation, and untrusted web content.

2. What are we working on?

This model starts from a generic, high-level Web API diagram from the Threat Model for the Web, and the system under analysis is created by adding the specific WebIDL, methods, and dictionaries from the specification, detailed in a methods-level view.

2.1. Scenario

This threat model considers an agentic Web in which AI agents can navigate and interact with web pages and web applications on a user’s behalf. WebMCP describes two relevant deployment models: an AI agent integrated into the browser, and an author-provided agent running in the page, for example through JavaScript. The latter can be illustrated, without treating it as a WebMCP implementation or a normative example, by Alibaba’s Page Agent: an in-page JavaScript agent that operates a web interface through the page’s DOM.

WebMCP provides an MCP-like interaction model for a web application. Rather than requiring an agent to infer an action from the rendered interface — for example, by inspecting the DOM or using screenshots to find a product-search control — a page can expose a structured search-products tool with a description and input schema. The agent can discover that tool and invoke it with structured arguments, while the page executes its existing application logic and returns a structured result.

A page can expose this functionality in two ways. The imperative API lets page code register tools directly in JavaScript. The declarative API allows the browser to derive tools from existing HTML forms and standard inputs.

Both mechanisms are intended to make existing web application functionality available to agents without requiring the agent to operate the user interface as a sequence of low-level interactions. This distinction also frames the threat model. Some threats are inherent to agentic web navigation, independently of WebMCP. Others arise when an agent uses a web page through an MCP-like tool interface. A third set is specific to the WebMCP surface itself, including tool registration, discovery, invocation, browser mediation, and the declarative and imperative exposure mechanisms. These categories can overlap, but separating them helps identify which risks WebMCP may reduce, which remain outside its scope, and which new risks its design can introduce.

3.1. Candidate deployment response: independent policy-based assessment

An implementation or deployment may introduce an independent Assessor that compares an observable decision record—including the applicable user goal, exposed tool provenance, selected tool and arguments, authorization or mediation, returned result, and observable effect—against a versioned external referential, such as a certified policy set or regulatory rulebook. This can detect a manipulated or materially incorrect action even where the invocation remains within the user’s formal mandate. It is a deployment-level control, not part of WebMCP conformance. Unless the assessment is placed before an irreversible side effect and can block the invocation, it is detective rather than preventive. It primarily responds to T-27 and may support the provenance and attribution concerns in T-07 and T-19. The value of the response depends on the evidence path. Evidence must be sufficiently complete, authentic, timely, and bound to the production agent, inference provider, model and configuration version, browser context, tool surface, and specific invocation. Provider-generated explanations or hidden model reasoning are not, by themselves, authoritative evidence. A formal agreement between the Subject Agent or inference provider and the Trust Authority can allocate accountability, audit rights, and consequences and can transfer part of the risk. It does not technically guarantee evidence integrity or completeness, and it only partially responds to T-24 when the provider controls the evidence being assessed. Remaining threats include selective omission, fabrication, replay, evaluation-specific behavior, differences between the evaluated sample and production deployment, stale or ambiguous referentials, Assessor or Trust Authority compromise, and detection only after a consequential effect. Compliance with the referential does not by itself establish alignment with the user’s actual intent or with the human-facing semantics of the action (T-03 and T-26). The evidence flow may also disclose or retain user goals, arguments, results, or cross-context identifiers, creating additional T-05 and T-17 concerns; minimization, partitioning, access control, and retention limits would be required. If this response is developed further, the Assessor, Trust Authority, referential, evidence source or store, and evidence and assessment-result flows should be modeled as a separate deployment overlay. That overlay should make its trust boundaries, policy versioning, evidence-generation responsibility, privacy assumptions, accountability recipients, and remaining threats explicit before the control is presented as providing assurance.

4. Did we do a good enough job?

This draft threat model provides:

  • a high-level view of the WebMCP methods and surfaces in scope;

  • a set of threats classified by their primary origin: the WebMCP-specific surface, agentic web navigation, or risks associated with exposing web-application functionality through a Web API;

  • a mapping between the identified threats and the Security and Privacy Considerations section, making visible where the specification addresses a threat and where further work may be needed.

The next pass should focus on the corresponding remediations and on whether they are appropriately placed in the specification. It may also be useful to develop a more detailed analysis of the algorithms and methods involved, either through focused diagrams or through a textual analysis where a diagram would not clarify the relevant trust boundaries, data flows, or decision points.

Finally, the model should assess the two deployment scenarios separately: an in-page agent and an AI agent integrated into the browser. After consolidating the general model, this comparison can show whether either scenario introduces additional threats, changes their severity, or calls for scenario-specific mitigations.
